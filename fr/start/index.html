Démarrer

Tout tourne en local. Pas de compte, pas de clé d’API, pas de modèle d’IA. Suivez les étapes dans l’ordre : chacune prend environ une minute.

Ce qu’il vous faut

Node.js 20 ou plus récentgitun terminal
Vérifiez votre version de Node.js :
$ node -v
1

Lancer la démo dans votre terminal

Récupérez le code, puis jouez deux fois la même attaque : sans ShieldTrail, puis avec.

Récupérer le code
$ git clone https://github.com/SergeMiro/ShieldTrail.git
$ cd ShieldTrail
$ npm install
Sans ShieldTrail — les numéros de carte fuient
$ npm run demo -- --mode off
Avec ShieldTrail — le vol est stoppé, l’application continue
$ npm run demo -- --mode enforce
À la fin du dernier lancement, vous devez voir :
BLOCKED     5. POST customers to exfil.attacker.dev
            BLOCKED by exfil-after-injection. Request never left the app.
OK          6. Reply to customer

Data that reached the attacker: none
2

Voir le panneau dans une vraie application Next.js

Une petite interface d’administration de boutique avec deux agents IA. Dans le coin de chaque page où un agent a agi, un bouclier montre ce qui s’est passé. Vous y approuvez aussi un remboursement.

Construire ShieldTrail et lancer l’exemple
$ npm run build
$ npm run dev -w shieldtrail-next-example
Ouvrir la page avec l’attaque, puis cliquer sur le bouclier dans le coin
$ http://localhost:3100/support
Tableau de bord complet avec le graphe d’attaque
$ http://127.0.0.1:4320

L’ajouter à votre application

ShieldTrail n’est pas encore publié sur npm : construisez-le depuis le dossier cloné et installez-le à partir de là.

Construire, puis installer dans votre projet
$ npm run build
$ cd ../votre-app
$ npm install ../ShieldTrail/packages/shieldtrail
Puis créez un garde, enveloppez ce que fait votre agent et ajoutez le panneau :
// lib/guard.ts — reads shieldtrail.policy.json, starts the dev panel in development
import { createGuard } from 'shieldtrail/node';
export const guard = createGuard({
  secrets: [{ name: 'STRIPE_KEY', value: process.env.STRIPE_KEY, domains: ['api.stripe.com'] }],
});

// where your agent runs
const trace = guard.startTrace({ agent: 'support-bot', task: 'Answer a ticket', allowedTools: ['tickets.*'] });
await trace.context({ source: fileUrl, text: fileText });              // what the agent reads
const rows = await trace.tool('db.query', args, () => db.query(args)); // each tool call
await trace.run(() => agent.next());                                    // every fetch inside is checked
await trace.usage(completion.usage);                                    // tokens, for budgets

// app/layout.tsx — the panel, development only (Next.js: serverExternalPackages: ['shieldtrail'])
{process.env.NODE_ENV === 'development' && <script src="http://127.0.0.1:4320/panel.js" async />}
4

Déployer sans risque

Commencez en observation, lisez ce qui aurait été bloqué, puis activez le blocage règle par règle. Avant chaque mise en production, rejouez le trafic enregistré avec les nouvelles règles.

Qu’est-ce qui aurait été bloqué ?
$ npm run shieldtrail -- report events.jsonl
Quelles règles fonctionnent, lesquelles ne se déclenchent jamais ?
$ npm run shieldtrail -- check events.jsonl
Les nouvelles règles casseraient-elles du trafic réel ? (code de sortie 1 = oui)
$ npm run shieldtrail -- replay events.jsonl
5

Écrire vos propres règles

Les règles vivent dans shieldtrail.policy.json, à côté de package.json : ce qu’il faut repérer, et s’il faut avertir, bloquer ou demander à une personne. La première règle qui correspond l’emporte ; "defaults" ajoute les règles intégrées. Les interrupteurs Observer / Bloquer du panneau sont enregistrés dans ce même fichier.

shieldtrail.policy.json
{
  "mode": "shadow",
  "allowedDomains": ["api.acme.com"],
  "budget": { "maxCallsPerTool": 20, "maxCostUsd": 2 },
  "rules": [
    {
      "id": "no-external-forward",
      "description": "Inbox content forwarded outside the company",
      "match": {
        "kind": "tool_call",
        "target": "email.send",
        "args": { "to": "!*@acme.com" },
        "after": { "kind": "tool_call", "target": "email.inbox" }
      },
      "action": "block",
      "mode": "enforce"
    },
    {
      "id": "refund-needs-human",
      "match": { "kind": "tool_call", "target": "payments.refund" },
      "action": "ask"
    },
    "defaults"
  ]
}
  • Règle de séquence : bloquer le transfert d’e-mails hors de l’entreprise, seulement après la lecture de la boîte de réception.
  • ask : l’étape attend qu’une personne l’approuve dans le panneau (ou via votre hook Slack). Sans réponse à temps, elle est bloquée.
  • Budget : appels, durée, jetons et argent par tâche. Déclarez l’usage du modèle avec trace.usage(response.usage).
  • Canaris, secrets liés et arrêt d’urgence restent dans le code : canaries: [createCanary()], secrets: [...], guard.halt().

Questions

Faut-il un modèle d’IA ou une clé d’API ?

Non. La détection repose sur des règles claires et déterministes. Vous pouvez brancher un modèle d’IA pour obtenir des résumés d’incident rédigés, mais c’est facultatif.

Mes données sont-elles envoyées quelque part ?

Non. Les événements restent dans votre processus, ou dans votre propre PostgreSQL. Ils ne sortent que si vous ajoutez un exportateur (webhook, SIEM, OpenTelemetry). Les secrets sont masqués avant stockage.

Qu’est-ce qu’il ne voit pas ?

Dans trace.run() et trace.tool(), chaque fetch est vérifié, y compris ceux des SDK comme OpenAI ou Stripe. Les bibliothèques qui n’utilisent pas fetch (axios sous Node, sockets bruts) et les autres programmes ne sont pas vus : ajoutez un proxy réseau à côté.

Le panneau part-il en production ?

Non. Son serveur ne démarre que si NODE_ENV vaut development, écoute sur 127.0.0.1 et ne répond qu’aux pages de localhost. La balise script de votre layout est derrière la même condition.

Quelles applications peuvent l’utiliser ?

Toute application Node.js 20+ : serveurs Express ou Fastify, route handlers Next.js, workers, et applications qui utilisent des outils MCP.
